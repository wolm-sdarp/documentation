# Инструкция по работе с проектом WLM_SDARP_PROJ для LLM

## 0. О файле

- Документ предназначен для LLM(s), которая/которые используются при работе над проектом.
- Файл описывает, как LLM взаимодействует с материалами проекта, каких принципов работы, правил и ограничений придерживается.
- Этот файл хранит базовые инструкции. Дополнительные инструкции от конкретного пользователя лежат в [[LLM_INSTRUCTIONS_PERSONAL]].
- Файл ссылается на другие источники информации о проекте — при чтении их также нужно изучить.

## 1. О проекте

### 1.1. Паспорт проекта
#### Название и расшифровка аббревиатур
**WoLM SDARP**
#### Цель проекта
Cоздать серию качественных книг и дополнительных материалов для самостоятельного глубокого и системного освоения анализа данных с нуля психологами широкого круга специализаций с опорой на современные методические подходы.
#### Тип проекта
Образовательный продукт с IT-основой.
- образовательная сторона — книги, тесты, задания, проектные работы.
- IT-основа — Git, GitHub, Quarto, публикация материалов в формате сайта.
#### Аудитория результатов
  - студенты-бакалавры и магистранты психологических специальностей — как дополнительная литература к университетским учебникам
  - аспиранты и молодые исследователи — как самоучитель «с нуля до pro»
  - практикующие исследователи из академии и индустрии — как справочник по сложным вопросам и неоднозначным решениям
  - преподаватели университетов — в качестве методических материалов и учебных пособий
  - все интересующие статистикой и анализом данных в психологии и социальных науках
#### Этап, задачи и сроки
Смотри GH Project [**WoLM SDARP PM**](https://github.com/orgs/wolm-sdarp/projects/1) в GH Organization.
- Подробнее об организации, репозитория и проектах см. 
#### Критерии успеха
- Задачи высоких приоритетов выполнены вовремя.
- Задачи средних приоритетов выполнены.
- Задачи низких приоритетов выполнены или перенесены в следующий milestone.

```
WLM_SDARP_PROJ/
├── gh-profile/           # project profile (tech repo)

├── documentation/           # project documentation vault
│	├── content/
```

#### Подробное описание директорий
##### Codebook
- Folder : название папки
- Type : тип папки или файла
	- `dir` — обычная локальная директория
	- `repo` — Git-репозиторий
	- `vault` — Obsidian-хранилище
	- `quarto` — Quarto-проект
- Remote : ссылка на связанный удаленный репозиторий (для Type:`repo`)
- Description : описание содержимого

### 2.2. Правила именования
- Только латиница, цифры, `_` и `-`; без пробелов и спецсимволов.
- Версия повышается при существенной переработке; мелкие правки версию не меняют.
- Не называть файлы «финал», «финал2», «новый» — для этого есть версии и `CHANGELOG.md`.

### 2.3. Что и в каком формате
| Тип материала                  | Формат                                      |
| ------------------------------ | ------------------------------------------- |
| Результаты работы по умолчанию | `.md` (один файл на одну задачу)            |
| Таблицы и расчёты              | `.xlsx` / `.csv` — только по прямой просьбе |
| Документы для отправки         | `.docx` / `.pdf` — только по прямой просьбе |
| Презентации                    | `.pptx` — только по прямой просьбе          |
| Код                            | обычные файлы кода в `claude`               |

## 6. Порядок взаимодействия по задачам

### 6.1. Как ставить задачу (шаблон)
```
Задача: [что нужно сделать]
Материалы: [какие файлы / папки использовать]
Результат: [формат, объём, куда положить — по умолчанию один md-файл]
Ограничения: [сроки, стиль, что нельзя трогать]
Критерий готовности: [как проверим]
```

### 6.2. Как отвечаю я
- Короткое резюме результата в чате + ссылка на файл.
- Список допущений и вопросов, оставшихся открытыми.
- Что изменилось (если правились существующие файлы).
- Предлагаю следующий шаг, но не выполняю его без запроса.

### 6.3. Уточняющие вопросы
Задаю не более одного-двух за раз и только если без ответа результат может оказаться неверным. В остальных случаях делаю разумное допущение и явно его называю.

### 6.4. Длинные и сложные задачи
Разбиваем на этапы: план → черновик → ревью → финал. После каждого этапа — контрольная точка, чтобы не потерять время на неверное направление.

## 7. Память и преемственность между чатами

- Я не помню содержимое прошлых чатов автоматически, если это не сохранено в памяти проекта. Поэтому:
  - актуальную версию этого документа и `CHANGELOG.md` держите в проекте;
  - в начале нового чата достаточно написать: «Работаем по инструкции проекта, вот задача…».
- Если хотите, чтобы я что-то запомнил (терминологию, предпочтения по формату, договорённости), скажите явно: «запомни, что …».
- Секреты, идентификационные данные и другую чувствительную информацию в память не сохраняю.
