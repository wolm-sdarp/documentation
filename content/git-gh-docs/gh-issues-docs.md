> Документ описывает, как в [организации WoLM SDARP](https://github.com/wolm-sdarp) классифицируются задачи: какие **Issue Types**, **Labels** и **Issue fields** используются, как их выбирать и как расширять систему.
> 
> **Версия:** 1.0 · **Дата:** 2026-10-01 · **Статус:** предложение к внедрению

## 1. Исходные условия и допущения

- Проект объединяет три вида работы: **методическую** (learning design, разработка заданий), **авторско-редакторскую** (тексты книг) и **техническую** (код, Quarto-проекты, деплой). Система строится вокруг этих трёх потоков.
- Организация использует несколько репозиториев (`book0`, `book1`, `assessment0`, `assessment1`, `annex`, `documentation`, хаб и профиль организации; позже `book2`, `book3`, `assessment2`, `manim` и др.), основная ветка — `master`, разработка — в `dev` (см. [[LLM_INSTRUCTIONS_RU]]).
- Работа ведётся одним автором, но система рассчитана на команду: методисты, редакторы, переводчики, рецензенты, разработчики.
- Каналы публикации alpha/beta/stable и автоматическое определение версии (`bump:*`) обсуждались в архитектурных драфтах, но ещё не приняты. Всё, что на них опирается, описано как **резерв** (§4.5) и включается по условиям из §9.
- Идентификаторы (названия типов и меток, их описания в GitHub) — на английском: организация публичная, а язык материалов будет расширяться. Пояснения в этом документе и заголовки issues — на русском (рабочий язык проекта).

## 2. Принципы

1. **Одно измерение — одно место.** Каждый атрибут задачи хранится в одном механизме GitHub, а не дублируется (таблица ниже).
2. **Тип отвечает на вопрос «что это за работа», метки — «где это затрагивает» и «откуда пришло».** Тип у задачи один, меток — столько, сколько нужно (обычно 1–3).
3. **Метки собраны в оси с префиксом** (`ld:`, `content:`, `tech:`, `lang:`, `src:`, `status:`). Новая метка всегда принадлежит оси; синонимов нет.
4. **Минимум на старте.** Активно только то, что нужно сегодня. Остальное описано заранее, помечено как резерв и имеет явное условие включения.
5. **Три потока симметричны:** у методической, авторской и технической работы есть свои типы и своя ось меток; дефекты выделены отдельно.
6. **Система развивается по правилам** (§9), а не по ситуации: нет разовых меток вроде `todo` или `tmp`.

## 3. Issue Types

Типы создаются на уровне организации (`Organization Settings > Planning > Issue types`), одинаковы для всех репозиториев. Технический лимит GitHub — 25 типов; рабочий лимит системы — **12 активных** (см. §9).

### 3.1. Три потока и {==дефекты==}{{author="angelgardt">>заменить слово<<}}

| Поток                                                  | Типы                             | Ось меток              | Типичная роль               |
| ------------------------------------------------------ | -------------------------------- | ---------------------- | --------------------------- |
| Методический                                           | Learning Design, Assessment      | `ld:*`                 | методист                    |
| Авторский и редакторский                               | Writing, Editing, Localization   | `content:*`, `lang:*`  | автор, редактор, переводчик |
| Технический                                            | Feature, Maintenance, Release    | `tech:*`               | разработчик                 |
| {==Дефекты==}{{author="angelgardt">>заменить слово<<}} | Mistake (контент), Bug (техника) | `content:*` / `tech:*` | автор / разработчик         |
| Сквозные                                               | Epic, Research, *Review*, Task   | любые                  | любая                       |

Курсивом выделены типы из резерва.

### {==3.2. Каталог типов==}{{author="angelgardt">>аппрув, забрать в документацию<<}}

Цвет кодирует поток: фиолетовый — методический, синий — авторский, красный — дефекты, зелёный — технический, жёлтый — исследование и рецензирование, серый — общие.

| Тип                 | Цвет   | Статус  | Описание в GitHub (EN)                                                                    | Когда использовать                                                                                                |
| ------------------- | ------ | ------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Epic**            | gray   | активен | A container for related issues: a chapter, a book part, a review round                    | Группирует sub-issues, собственной работы не содержит; закрывается, когда закрыты все вложенные задачи            |
| **Learning Design** | purple | активен | Learning design: vision, personas, competencies, outcomes, assessment strategy, structure | Проектирование образовательного продукта по этапам методологии (ось `ld:`); результат — проектный артефакт        |
| **Assessment**      | purple | активен | Development and validation of exercises, test items and assessment forms                  | Создание, проверка и калибровка заданий и форм контроля — и в `assessment*`, и упражнений внутри книг             |
| **Research**        | yellow | активен | A time-boxed investigation whose result is knowledge or a decision                        | Обзор литературы, проверка источников, выбор пакета или подхода, технический spike; результат — вывод или решение |
| **Writing**         | blue   | активен | Authoring new content: text, formulas, figures, examples, datasets                        | Создание новой единицы содержания; форма результата уточняется меткой `content:*`                                 |
| **Editing**         | blue   | активен | Planned improvement of existing content without fixing an error                           | Структура, стиль, ясность, сокращение, переработка по замечаниям рецензента, вычитка                              |
| **Mistake**         | red    | активен | An error in existing content: factual, mathematical, code or language                     | Содержание неверно: статистика, математика, неверный вывод, опечатка, битая ссылка                                |
| **Bug**             | red    | активен | A technical defect: build, rendering, CI, deployment or code that does not work           | Сборка падает, страница рендерится неверно, workflow не срабатывает, код не запускается                           |
| **Feature**         | green  | активен | New tooling or functionality: extension, template, automation                             | Новая техническая возможность: расширение Quarto, шорткод, шаблон, автоматизация                                  |
| **Maintenance**     | green  | активен | Technical upkeep without a change in behavior: dependencies, refactoring, settings        | Обновление `renv` и пакетов, рефакторинг, настройка репозитория, разбор Dependabot                                |
| **Task**            | gray   | активен | A task that fits no other type (use sparingly)                                            | Запасной тип; доля больше 15% открытых задач — сигнал пересмотреть систему (§9.5)                                 |
| **Localization**    | blue   | резерв  | Translation and adaptation of content into another language version                       | Перевод и адаптация (`en-US`, `ru-petr1708`); метка `lang:*` обязательна                                          |
| **Review**          | yellow | резерв  | Organizing and conducting a scientific, methodological, editorial or technical review     | Сам процесс рецензирования; замечания рецензентов оформляются отдельными Mistake / Editing                        |
| **Release**         | green  | резерв  | Preparing and publishing a release of a book or another product                           | Выпуск версии с чек-листом: сборка, проверки, тег, публикация                                                     |


### {==3.3. Как выбрать тип==}{{author="angelgardt">>аппрув, забрать в документацию<<}}

Идти сверху вниз, остановиться на первом «да».

1. Задача только объединяет другие задачи? → **Epic**.
2. Результат — знание или решение, а не артефакт? → **Research**.
3. Что-то уже существующее неверно или не работает?
   - неверен контент → **Mistake**;
   - не работает техника → **Bug**.
4. Создаётся новое:
   - элемент образовательного дизайна (цели, компетенции, структура, стратегия оценки) → **Learning Design**;
   - задания и формы контроля → **Assessment**;
   - текст, формулы, иллюстрации, примеры, данные → **Writing**;
   - инструмент или автоматизация → **Feature**.
5. Существующее улучшается без исправления ошибки:
   - контент → **Editing**;
   - техника → **Maintenance**.
1. Создаётся языковая версия → **Localization**.
2. Организуется рецензирование → **Review**; выпуск версии → **Release**.
3. Ничего не подошло → **Task** и пометка для пересмотра системы.

### 3.4. Граничные случаи

| Ситуация                                                              | Решение                                                                                                   |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| R-код в главе не запускается                                          | **Bug** + `content:code` (+ `reproducibility`). Если из-за этого неверен вывод в тексте, отдельная **Mistake** |
| В главе неверное статистическое утверждение                           | **Mistake** + `content:text`; для опубликованных версий добавить `erratum` (резерв)                       |
| Опечатка                                                              | **Mistake** + `content:text` (без `erratum`)                                                               |
| Рецензент пишет «объясните яснее» (ошибки нет)                        | **Editing**                                                                                               |
| Рецензент предлагает новый раздел                                     | **Writing**                                                                                               |
| Нужен новый шорткод или блок для врезок «Миф» / «История»              | **Feature** + `tech:quarto`; наполнение врезок — отдельные **Writing**                                    |
| Новый датасет для примеров                                            | **Writing** + `content:data`                                                                              |
| Скрипт `manim` для видеоиллюстрации                                   | сама иллюстрация — **Writing** + `content:video`; инструмент или конвейер — **Feature** + `tech:manim`     |
| Выбор пакета для таблиц в книге                                       | **Research**; по итогам — **Feature** или **Maintenance**                                                 |
| Проектируется блок заданий для главы                                  | стратегия оценки — **Learning Design** + `ld:4-assessment`; сами задания — **Assessment**                 |
| Ошибка в переводе                                                     | **Mistake** + `lang:en-US` (или другой язык)                                                              |
| Читатель задал вопрос                                                 | не issue, а **Discussion** (Q&A); если вопрос выявил пробел — завести **Editing** или **Writing**          |

Правило при сомнении: тип определяется тем, **что именно придётся изменить** и **кому это поручить**. Если изменить нужно и код, и текст, задача делится на две.

## 4. Labels

Метки существуют на уровне репозитория. Ограничения GitHub: имя до 50 символов, описание до 100.

### 4.1. Соглашения об именовании

- Формат `ось:значение`, строчными латинскими буквами, слова через дефис: `tech:ci`, `content:math`.
- Исключение 1: коды языков — по BCP 47 в регистре стандарта (`lang:ru-RU`, `lang:en-US`, `lang:ru-petr1708`), как принято в [[LLM_INSTRUCTIONS_RU]].
- Исключение 2: `good first issue` и `help wanted` сохраняют стандартные имена, так как GitHub выделяет их на страницах репозитория.
- Значения — существительные в единственном числе; один смысл — одна метка.
- Описание на английском, одно предложение, до 100 символов.
- Цвет задаётся осью: все метки одной оси одного цвета.

| Ось               | Цвет (hex) |
| ----------------- | ---------- |
| `ld:`             | `#8957e5`  |
| `content:`        | `#1f6feb`  |
| `tech:`           | `#2da44e`  |
| `lang:`           | `#bf8700`  |
| `src:`            | `#d4761c`  |
| `status:`         | `#6e7781`  |
| сквозные          | `#bf3989`  |
| релизные (резерв) | `#1b7c83`  |

### 4.2. Оси, активные сейчас

#### `ld:` — этап образовательного проектирования

Совпадает с пятью этапами методики проектирования образовательного продукта (см. [[ld-docs]]); номера сохраняют порядок в списке меток.

| Метка             | Описание (EN)                                                   |
| ----------------- | --------------------------------------------------------------- |
| `ld:vision`       | Global vision: goals, personas, jobs to be done, product canvas |
| `ld:competencies` | Competency profile                                              |
| `ld:outcomes`     | Learning outcomes and their taxonomy levels (Bloom, SOLO, Fink) |
| `ld:assessment`   | Assessment strategy and alignment with outcomes                 |
| `ld:content`      | Content structure, sequencing and instructional events          |

#### `content:` — форма содержимого

| Метка                | Описание (EN)                                          |
| -------------------- | ------------------------------------------------------ |
| `content:text`       | Prose: explanations, examples, callouts                |
| `content:math`       | Formulas, derivations, notation                        |
| `content:code`       | R code and its output in the text                      |
| `content:figure`     | Plots, diagrams, illustrations                         |
| `content:data`       | Datasets used in examples and exercises                |
| `content:exercise`   | Exercises, solutions, hints                            |
| `content:glossary`   | Terms, glossary, index, notation tables                |
| `content:references`  | Bibliography, citations, cross-references and links    |

#### `tech:` — техническая область

| Метка          | Описание (EN)                                                      |
| -------------- | ------------------------------------------------------------------ |
| `tech:quarto`  | Quarto projects: config, extensions, filters, shortcodes, crossref |
| `tech:style`   | Visual style: SCSS, themes, typography, brand                      |
| `tech:ci`      | GitHub Actions and automation                                      |
| `tech:deploy`  | Building and publishing: Pages, branches, releases                 |
| `tech:deps`    | Dependencies: renv, R and Node packages, Dependabot                |
| `tech:repo`    | Repository settings: branches, rulesets, templates, labels         |
| `tech:docs`    | Project documentation vault (Obsidian, Quartz)                     |

#### `lang:` — языковая версия

| Метка             | Описание (EN)                          |
| ----------------- | -------------------------------------- |
| `lang:ru-RU`      | Source language version                |
| `lang:en-US`      | English (US) version                   |
| `lang:ru-petr1708` | Pre-reform Russian orthography version |

Правило: `lang:*` обязательна для Localization; для остальных типов ставится, только если задача относится к конкретной языковой версии. Отсутствие метки означает «исходный материал или все версии».

#### `src:` — источник обращения

| Метка          | Описание (EN)                                                    |
| -------------- | ---------------------------------------------------------------- |
| `src:reader`   | Reported by a reader                                             |
| `src:reviewer` | Reported by a reviewer (scientific, methodological, editorial)   |

Нужна, потому что автор issue в GitHub не всегда совпадает с автором замечания: замечания могут переноситься вручную.

#### `status:` — исключения в процессе

| Метка                | Описание (EN)                                                  |
| -------------------- | -------------------------------------------------------------- |
| `status:needs-triage` | New issue waiting for type, labels and priority                |
| `status:needs-info`  | Waiting for details from the reporter                          |

Основное состояние задачи берётся из поля Status в Project; блокировки — из issue dependencies. Метка `status:needs-triage` ставится автоматически шаблонами (§7) и снимается при триаже.

#### Сквозные и сообщественные метки

| Метка              | Описание (EN)                                   | Примечание                                                    |
| ------------------ | ----------------------------------------------- | ------------------------------------------------------------- |
| `accessibility`    | Barrier affecting people with disabilities      | существует; охватывает и контент (alt-тексты), и технику (контраст, структура страниц) |
| `reproducibility`  | Results, code or environment cannot be reproduced | новая; для книги по анализу данных это отдельный класс проблем |
| `good first issue` | Good for newcomers                              | существует; кандидаты: Mistake (язык), небольшие Editing       |
| `help wanted`      | Extra attention is needed                       | существует                                                    |
| `dependencies`     | Pull requests that update a dependency file     | создаёт Dependabot                                            |

Метки `javascript` и `github_actions` создаёт Dependabot, они нужны только в репозиториях, где он включён (сейчас `documentation`); вручную их не редактируют.

| Feature            | —     | —          | **R**   | —       | O      |

### 4.5. Резерв

Метки создаются заранее, но используются после выполнения условия включения (§9.2).

| Метка / ось                                                  | Описание (EN)                                                              | Условие включения                          |
| ------------------------------------------------------------ | -------------------------------------------------------------------------- | ------------------------------------------ |
| `bump:major` / `bump:minor` / `bump:patch` / `bump:none`     | PR: version impact — breaks reader links / adds a content unit / fixes / none | принят SemVer и автоматизация релизов      |
| `channel:alpha` / `channel:beta` / `channel:stable`          | Publication channel the issue relates to                                   | принята модель каналов публикации          |
| `erratum`                                                    | Substantive error in published content; needs a changelog entry            | выпущена первая stable-версия              |
| `src:annotation`                                             | Transferred from a Hypothesis annotation                                   | подключена вычитка через Hypothesis        |
| `content:video`                                              | Video illustrations (manim)                                                | создан репозиторий с видеоиллюстрациями    |
| `tech:manim`                                                 | Python and manim scripts for video illustrations                           | создан репозиторий `manim`                 |

Соответствие названиям из архитектурных драфтов: `beta-feedback` = `channel:beta` + `src:reviewer`; `type:brand` = `tech:style`; `book:*` не нужны (продукт задаёт репозиторий).

Issue Types на pull requests не распространяются, поэтому для PR (категории release notes, версия) используются те же метки осей и `bump:*`.

## {==5. Issue fields==}{{author="angelgardt">>в целом ок, проверить русское и английское описание<<}}

## 6. Иерархия, milestones и доска

- **Epic → задачи.** Глава книги, раунд рецензирования или крупный блок — Epic; вложенные задачи — sub-issues. Глубина — не более двух уровней. Epic лежит в репозитории основного результата; sub-issues могут быть в других репозиториях организации (например, задания к главе — в `assessment1`).
- **Milestone** — целевая версия или этап внутри репозитория; закрывается вместе с выпуском. Незавершённые задачи низкого приоритета переносятся в следующий milestone.
- **Project «WoLM SDARP PM»** — одна доска на все репозитории; рекомендуемые представления:
  - Board по Status;
  - Table с группировкой по Type;
  - Roadmap по Target date;
  - Triage: `label:status:needs-triage`;
  - Review queue: Status = In review.
- Поле Status на доске — единственное пользовательское поле, которое стоит добавить. Тип, репозиторий, milestone и приоритет берутся из встроенных механизмов.

## 7. Шаблоны и триаж

Шаблоны issues (issue forms) хранятся в репозитории `.github` организации и применяются во всех репозиториях, где нет своих. Шаблоны, унаследованные от Quartz в `documentation`, заменяются на общие. Каждая форма сама назначает тип и, при необходимости, метки.

| Форма                    | Тип             | Авто-метки             | Обязательные поля                                                              |
| ------------------------ | --------------- | ---------------------- | ------------------------------------------------------------------------------ |
| Content error            | Mistake         | `status:needs-triage`  | где (ссылка, глава), что неверно, как должно быть, обоснование                 |
| Improvement suggestion   | Editing         | `status:needs-triage`  | где, что улучшить, зачем                                                       |
| Content task             | Writing         | —                      | единица содержания, план, источники, критерий готовности                       |
| Learning design task     | Learning Design | —                      | этап (`ld:*`), входные данные, ожидаемый артефакт, связь с образовательными результатами |
| Assessment task          | Assessment      | —                      | какие результаты покрывает, уровень таксономии, формат заданий, критерии оценки |
| Technical problem        | Bug             | `status:needs-triage`  | шаги воспроизведения, ожидаемое и фактическое, версии R и Quarto, ОС           |
| Technical request        | Feature         | —                      | проблема, предложение, альтернативы                                            |
| Research question        | Research        | —                      | вопрос, ограничение по времени, ожидаемый результат                            |
| Other                    | Task            | —                      | описание                                                                       |

Для читателей в `config.yml` добавляется ссылка на Discussions (вопросы по материалу). Формы для резервных типов (Localization, Review, Release) создаются при их включении.

**Триаж** выполняется регулярно (для одного автора — раз в неделю) и завершается, когда у задачи есть:

1. тип;
2. обязательные оси меток по матрице §4.4;
3. Priority (и Effort, если задача берётся в работу);
4. milestone, если задача запланирована;
5. снятая метка `status:needs-triage`; задача добавлена в Project.

## 8. Роли и рост команды

| Роль                    | Основные типы                                   | Пример фильтра для сохранённого представления                    |
| ----------------------- | ----------------------------------------------- | ---------------------------------------------------------------- |
| Автор                   | Writing, Mistake, Editing, Research             | `is:open type:Writing label:"content:math"`                      |
| Методист                | Learning Design, Assessment, Review             | `is:open type:"Learning Design" label:"ld:3-outcomes"`           |
| Редактор                | Editing, Review, Mistake (язык)                 | `is:open type:Editing`                                           |
| Внешний рецензент       | создаёт Mistake / Editing через формы           | `is:open label:src:reviewer`                                     |
| Разработчик             | Feature, Bug, Maintenance, Release              | `is:open type:Bug label:"tech:ci"`                               |
| Переводчик              | Localization                                    | `is:open label:"lang:en-US"`                                     |
| Новый участник          | любые с `good first issue`                      | `is:open label:"good first issue"`                               |

Пока в проекте один участник, все роли совмещены; система остаётся полезной как способ фильтровать работу по режимам («сегодня пишу», «сегодня проектирую», «сегодня чиню сборку»). С появлением команды роли закрепляются за типами и осями без изменения самой системы.

## 9. Правила расширения

### 9.1. Когда вводить новый тип

Все условия должны выполняться одновременно:

1. у работы особый критерий готовности или порядок шагов;
2. у неё свой исполнитель либо своя форма;
3. её нельзя выразить сочетанием существующего типа и метки;
4. ожидается не менее пяти таких задач в квартал;
5. после добавления активных типов не больше 12.

### 9.2. Когда включать резерв

| Событие                                                    | Что включить                                                                              |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Начались переводы                                          | тип Localization и форму; `lang:*` становится обязательной для него                       |
| Появились внешние рецензенты и раунды рецензирования       | тип Review, `src:annotation`, `channel:*`; Epic на каждый раунд; статус «Beta feedback» на доске |
| Принята автоматизация версий и выпусков                    | тип Release, `bump:*`, `erratum`, `channel:*`; проверка метки `bump:*` в CI               |
| Создан репозиторий `manim`                                 | `tech:manim`, `content:video`                                                             |
| Появились разработчики                                     | CODEOWNERS по осям `tech:*`; при необходимости — отдельный тип (например, Spike), но не заранее |

### 9.3. Когда добавлять метку или ось

- **Новое значение в существующей оси:** есть не менее трёх задач либо сохранённое представление или автоматика, которым оно нужно. Иначе хватает комментария в задаче.
- **Новая ось:** есть сквозной вопрос, который нельзя задать существующими осями; указан владелец, область применения (§4.3), цвет, не более десяти значений. Пример: предметные срезы (`topic:glm`, `topic:bayes`) заводятся только если по главам и Epic их получить нельзя.
- **Новый репозиторий** (`book2`, `book3`, `assessment2`): применяются наборы из §4.3; шаблоны наследуются от `.github`; ничего нового придумывать не требуется.

### 9.4. Что не делать

- метки для типа, приоритета, трудоёмкости, статуса, продукта или версии — для них есть свои механизмы (§2);
- метки по главам и разовые метки (`todo`, `tmp`, `later`);
- синонимы одной метки (`typo` и `mistake`);
- глубокая иерархия sub-issues и «эпики эпиков».

### 9.5. Пересмотр и вывод из обращения

- **Раз в квартал и перед каждым stable-релизом** проверяются: доля `Task` среди открытых задач (порог 15%), задачи без обязательных меток, метки без использования за два квартала.
- Неиспользуемая метка удаляется после переноса задач на другую метку или в комментарий; решение записывается в историю изменений ниже.
- Изменения вносит владелец проекта; при росте команды — через pull request в репозиторий `.github` (эталонный набор меток) с записью в этом документе.

### 10.3. Порядок внедрения

1. **Issue types.** `Organization Settings > Planning > Issue types`: изменить описания существующих типов, создать новые активные.
2. **Эталонный набор меток.** В репозитории `.github` создать метки из §4.2 по наборам §4.3. Сначала переименовать устаревшие метки в рабочих репозиториях (`documentation` → `tech:docs`), затем скопировать эталон в остальные репозитории командой `gh label clone wolm-sdarp/.github -R wolm-sdarp/<репозиторий>` (команда добавляет метки и не удаляет лишние). При росте числа репозиториев перейти на файл `labels.yml` с синхронизацией через Actions.
3. **Очистка.** Удалить метки, отмеченные в §10.2.
4. **Шаблоны.** Добавить формы из §7 в `.github`, удалить унаследованные от Quartz шаблоны в `documentation`.
5. **Существующие задачи.** Назначить типы и оси; массовое редактирование удобно делать в таблице Project.
6. **Доска.** Добавить представления из §6 и поле Status.
7. **Документация.** Заменить разделы «Issue Types» и «Labels» в [[git-gh-docs]] ссылкой на этот документ; пустые таблицы «Labels» в конце [[git-gh-docs]] удалить.
