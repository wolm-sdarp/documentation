# Работа с Git: ветки, коммиты, pull requests

> **Статус:** драфт v0.1 · 2026-10-01 · предлагается к обсуждению, ничего из этого пока не принято.
> Документ дополняет [[git-gh-docs]] и [[gh-issues-docs]]: те описывают организацию, типы задач и метки, этот — как выглядит сама история изменений.

## 0. Кратко

Одна страница, которую достаточно помнить в повседневной работе.

1. Две постоянные ветки: `master` (опубликованная версия) и `dev` (текущая разработка). Остальные ветки живут дни и удаляются после слияния.
2. Каждая задача — отдельная ветка от `dev`: `тип/короткое-описание`, например `feat/pretests`, `chore/setup-repo`, `fix/autocheck-item2`.
3. Тип ветки совпадает с типом коммита (раздел 5), так что запоминать один список, а не два.
4. Коммит пишется как `тип(область): что сделано`, по-английски, в повелительном наклонении, до 72 символов: `feat(ch05): add pretest for the p-value section`.
5. Один коммит — одно логическое изменение. Правка текста и перестройка файлов, форматирование и смысловая правка — разные коммиты.
6. В `dev` попадает только через pull request (PR), слияние — **squash**. Заголовок PR оформляется как коммит, потому что именно он станет записью в истории.
7. В `master` изменения попадают из `dev` одним PR при выпуске версии, слияние — **обычным merge-коммитом**, не squash.
8. В репозиторий не попадают: секреты, личные данные, собранные книги (`_book/`), тяжёлые видео, служебные файлы RStudio и macOS.
9. Каждая задача в GitHub (issue) упоминается в PR или коммите: `Refs #12`, а при закрытии — `Closes #12` (с оговоркой из раздела 6).
10. Если что-то пошло не так — сначала `git status` и `git reflog`, потом раздел 11. Почти всё обратимо, пока нет принудительной отправки (`push --force`).

## 1. Принципы

| Принцип | Что означает на практике |
| --- | --- |
| История — часть документации | Журнал коммитов читают рецензенты, соавторы и читатели (организация открытая). По нему должно быть понятно, что и зачем менялось в книге |
| Мелкие, короткоживущие ветки | Долгая ветка расходится с `dev`, конфликты растут. Задача размером «глава целиком» разбивается на под-задачи (sub-issues), у каждой своя ветка |
| Один набор слов везде | Типы в ветках, коммитах и PR совпадают между собой и согласуются с Issue Types и метками осей |
| Автоматизируемо, но без автоматизации на старте | Формат выбран так, чтобы позже можно было включить проверки, автоматические заметки к релизу и версии. Пока всё делается вручную |
| Простота важнее полноты | Типов и областей мало, исключения описаны явно. Правило, которое трудно запомнить, не соблюдается |
| Защита от необратимого | Принудительная отправка и переписывание опубликованной истории запрещены правилами репозитория |

## 3. Модель веток

Выбрана упрощённая схема из двух постоянных веток и коротких рабочих. Полноценный GitFlow (отдельные `release/*`, `hotfix/*`, `develop`) избыточен для небольшой команды, а работа только в `master` не оставляет места для «черновой» версии между публикациями.

```
master  ──●───────────────────●────────────  опубликованная версия (теги vX.Y.Z)
           \                 / ← merge-коммит при выпуске
dev     ────●──●──●──●──●──●─────────────  текущая разработка
              \    /  \  /
feat/pretests  ●──●    fix/autocheck-item2  рабочие ветки (squash → dev)
```

| Ветка | Назначение | Кто пишет | Время жизни | Защита |
| --- | --- | --- | --- | --- |
| `master` | Опубликованная, стабильная версия. С неё собирается сайт, на неё ставятся теги | Только через PR из `dev` (раздел 7) | постоянная | запрет force-push и удаления, обязательный PR |
| `dev` | Интеграция: сюда сливаются все готовые задачи | Только через PR из рабочих веток | постоянная | запрет force-push и удаления |
| `тип/описание` | Одна задача (один issue) | Автор задачи | дни, максимум 1–2 недели | нет; удаляется после слияния |
| `hotfix/…` | **Резерв.** Срочная правка уже опубликованной версии, когда `dev` ушёл вперёд | Автор | часы | как рабочая; PR в `master`, затем `master` вливается в `dev` |

Правила:

- Рабочая ветка создаётся **от свежего `dev`** и сливается обратно в `dev`.
- Прямые коммиты в `master` запрещены всегда. В `dev` допустимы только микроправки (опечатка в README, настройка репозитория) — пока команда состоит из одного человека; при появлении второго автора это исключение отменяется.
- Опубликованная история (`master`, `dev`, любая отправленная ветка, которой пользуется кто-то ещё) **не переписывается**: без `rebase`, `commit --amend` после отправки и `push --force`. Свою личную ветку до открытия PR можно править свободно.
- Репозиторий `documentation` пока имеет дополнительные ветки (`v5`, унаследована от Quartz; на неё указывает HEAD). При настройке нужно решить, какая ветка является основной на GitHub, и привести её к общей схеме (открытый вопрос 6).

## 4. Именование веток

### 4.1. Формат

```
<тип>/<короткое-описание>
<тип>/<область>-<короткое-описание>
```

- Тип — из таблицы раздела 5.2 (тот же список, что у коммитов).
- Описание: латиница, строчные буквы, слова через дефис, 2–4 слова. Это согласуется с правилом именования файлов проекта (README_PROJECT §2.2).
- Область (необязательна) — глава или модуль: `ch05`, `glossary`, `quarto`, `ci`.
- Кириллица, пробелы, заглавные буквы и подчёркивания не используются.

### 4.2. Примеры

| Ветка | Что делается |
| --- | --- |
| `feat/pretests` | Добавляются предварительные тесты (пример из пожелания автора) |
| `feat/ch05-glm-intro` | Новый раздел главы 5 |
| `fix/autocheck-item2` | Исправлена ошибка в автопроверке задания 2 |
| `fix/ch03-se-formula` | Исправлена формула стандартной ошибки |
| `edit/ch02-intro-style` | Редакторская правка вводной части |
| `ld/ch04-outcomes` | Образовательные результаты главы 4 |
| `assess/ch04-quiz` | Тестовые задания к главе 4 |
| `docs/git-workflow` | Документация по git |
| `chore/setup-repo` | Начальная настройка репозитория |
| `ci/render-book` | Сборка книги в GitHub Actions |
| `build/update-renv` | Обновление зависимостей R |

### 4.3. Замечания

- Для исправлений используется **`fix`**, а не `bug`: так называется тип коммита в Conventional Commits, а ветка и коммит должны совпадать. «Ошибка в содержании» (Mistake) и «ошибка в коде» (Bug) — оба `fix`.
- Номер issue в имя ветки не включается: связь с задачей обеспечивают PR и сноска `Refs #N` (раздел 6). Короткое имя читается лучше. Если команда предпочтёт номера, формат `feat/42-pretests` ничего не ломает (открытый вопрос 4).
- GitHub-кнопка «Create a branch» в issue предлагает имя вида `42-pretests`; его следует переименовать под формат проекта или создавать ветку из терминала.
- Одна ветка — одна задача. Если в процессе появилась побочная задача, для неё заводится отдельная ветка и issue.

## 5. Коммиты

### 5.1. Формат сообщения

Формат — [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/), без лишних сложностей:

```
<тип>(<область>): <описание>

<тело — необязательно>

<сноски — необязательно>
```

- **Заголовок** — одна строка, до 72 символов (в идеале до 50). Начинается со строчной буквы, без точки в конце, в повелительном наклонении: *add*, *fix*, *rewrite*, а не *added* и не *adds*. Проверка: фраза «Если применить этот коммит, он … » должна читаться естественно.
- **Область** (в скобках) необязательна. Если указана, то это глава, модуль или участок: `ch05`, `glossary`, `exercises`, `deps`, `quarto`.
- **Тело** отделено пустой строкой; объясняет *зачем* и *почему так*, а не *что* (что — видно из диффа). Строки до 72 символов.
- **Сноски** — ссылки на задачи и пометки: `Refs #12`, `Closes #12`, `Co-authored-by: …`.

### 5.2. Типы

Основа — стандартный набор Conventional Commits, дополненный четырьмя типами под специфику проекта (`edit`, `ld`, `assess`, `research`). Каждый тип соответствует Issue Type, чтобы по задаче сразу было понятно, какой префикс использовать.

| Тип | Когда используется | Соответствует Issue Type | Ежедневный |
| --- | --- | --- | :-: |
| `feat` | Новая содержательная единица или функциональность: раздел, глава, иллюстрация, возможность в сборке | Writing, Feature | да |
| `fix` | Исправление ошибки в тексте, формуле, коде, ключе, вёрстке | Mistake, Bug | да |
| `edit` | Редакторская правка без изменения смысла: стиль, структура, формулировки, ясность | Editing | да |
| `ld` | Артефакты учебного дизайна: цели, компетенции, образовательные результаты, структура, стратегия | Learning Design | да |
| `assess` | Задания, тесты, критерии оценивания, ключи | Assessment | да |
| `docs` | Документация проекта и репозиториев: README, инструкции, описания (но не тексты книг) | — (метка `tech:docs`) | да |
| `chore` | Прочее обслуживание репозитория: настройки, `.gitignore`, начальная инициализация | Maintenance | да |
| `research` | Заметки, обзоры источников, библиография | Research | по необходимости |
| `refactor` | Перестройка без изменения смысла или поведения: перенос и переименование файлов, реорганизация кода | Maintenance | по необходимости |
| `style` | Только форматирование кода и разметки (отступы, `styler`), без смысловых изменений | Maintenance (`tech:style`) | по необходимости |
| `build` | Зависимости и сборка: `renv.lock`, настройки Quarto | Maintenance (`tech:deps`, `tech:quarto`) | по необходимости |
| `ci` | Workflows GitHub Actions, публикация сайта | Maintenance (`tech:ci`, `tech:deploy`) | по необходимости |
| `test` | Автоматические проверки кода и ссылок | Maintenance / Feature | по необходимости |
| `revert` | Откат ранее сделанного коммита | — | по необходимости |

Если задача не укладывается ни в один тип, это сигнал, что она слишком большая (нужно разбить) или что вводится новый тип (правила — раздел 14). Типа `wip` нет: незавершённая работа оформляется как draft PR.

### 5.3. Области (scope)

Область — необязательное уточнение. Репозиторий уже сам указывает проект (`book1`, `annex`), поэтому в области его имя не повторяется.

| Группа | Примеры значений | Происхождение |
| --- | --- | --- |
| Содержательные репозитории | `ch01`, `ch12`, `intro`, `appendix`, `glossary`, `references`, `exercises` | идентификаторы глав — решить при создании первой книги (открытый вопрос 5) |
| Технические | `deps`, `renv`, `quarto`, `ci`, `deploy`, `repo`, `style` | совпадают со значениями метки `tech:*` |
| Документация | `vault`, `tech`, `content`, `drafts` | разделы репозитория `documentation` |

Область не обязательна и не должна превращаться в бюрократию: `chore: init` — нормальный коммит.

### 5.4. Примеры

Хорошие:

```
feat(ch05): add pretest for the p-value section
fix(ch03): correct the standard error formula
edit(ch02): shorten the introduction and fix repeated terms
ld(ch04): define learning outcomes LO-04.01..LO-04.05
assess(ch04): add self-check quiz on effect size
refactor: move figures to chapter folders
build(deps): update renv.lock after R 4.5 upgrade
docs: describe branch and commit naming
chore: init
```

Плохие и почему:

| Плохо | Проблема | Лучше |
| --- | --- | --- |
| `update` | Неясно, что и зачем | `edit(ch02): clarify definition of sampling error` |
| `fixed stuff` | Ни типа, ни объекта, не повелительное наклонение | `fix(ch03): correct the SE formula` |
| `chapter 5 done` | Событие, а не изменение; нет типа | `feat(ch05): add section on model comparison` |
| `Fix(ch03): Corrected The Formula.` | Регистр, точка, прошедшее время | `fix(ch03): correct the formula` |
| `fix: various fixes and new section and renv update` | Три изменения в одном коммите | три отдельных коммита |
| `финал2` | Версии хранит git, а не имена | см. README_PROJECT §2.2 |

### 5.5. Тело коммита и сноски

Тело нужно, когда причина неочевидна:

```
fix(ch03): correct the standard error formula

The previous version divided by n instead of sqrt(n); the worked
example and the numeric answer in exercise 3.2 were recalculated.

Closes #41
```

Типичные сноски:

| Сноска | Смысл |
| --- | --- |
| `Refs #12` | Коммит относится к задаче, но не завершает её |
| `Closes #12` | Задача выполнена этим изменением (см. оговорку в разделе 6) |
| `Refs wolm-sdarp/book1#12` | Задача из другого репозитория организации |
| `Co-authored-by: Имя <email>` | Соавтор коммита (в том числе при парном редактировании) |

### 5.6. Ломающие изменения

В Conventional Commits изменение, ломающее совместимость, помечается `!` после типа или строкой `BREAKING CHANGE:` в сноске. Для книги «ломающим» считается то, что рвёт внешние связи читателя и других материалов проекта:

- переименование или перенумерация глав и разделов, меняющие адреса страниц и якоря (`#sec-...`);
- удаление или переименование идентификаторов результатов обучения, заданий и ключей;
- изменение смысла опубликованного определения или обозначения.

```
refactor(ch05)!: renumber sections after splitting the GLM chapter

BREAKING CHANGE: section anchors #sec-glm-3..#sec-glm-6 changed;
links from annex/glossary are updated in the same release.
```

Эти же изменения в будущем соответствуют метке `bump:major` и мажорной версии (раздел 8). Пока автоматизации нет, знак `!` — просто сигнал для автора и рецензента.

### 5.7. Атомарность и работа с текстом

Книга — это текст, а у текста есть свои приёмы работы с git.

1. **Один абзац — несколько строк.** В исходных `.qmd`/`.md` каждое предложение пишется с новой строки («семантические переносы», semantic line breaks). Для читателя вёрстка не меняется, а diff показывает изменённое предложение, а не весь абзац. Это самая полезная привычка для работы над книгой в git.
2. **Не смешивать разные операции.** Перенос файла, смысловая правка и автоформатирование — отдельные коммиты. Иначе git не распознает переименование, а рецензент не отличит правку смысла от косметики.
3. **Коммитить часто, но осмысленно.** Достаточно закончить логический шаг: сформулирован раздел, исправлена формула, добавлено задание. Перед отправкой порядок не обязан быть идеальным: при слиянии через squash ветка схлопнется в один коммит (раздел 7).
4. **Смотреть, что попадает в коммит.** `git status`, затем `git diff --staged` перед каждым коммитом. Добавлять файлы по имени или `git add -p`, а не `git add .` вслепую: так в коммит не попадают черновики, большие файлы и служебные папки.
5. **Не коммитить результат вместо источника.** Источник — `.qmd`, `.R`, `.yml`; результат — HTML, PDF, `*_files/`. Исключение — кэш вычислений Quarto (раздел 9).

### 5.8. Язык сообщений и маркировка вклада ИИ

**Язык.** Предлагается английский для типа, области и заголовка (в публичной истории, в логах CI и при локализации на `en-US` он удобнее всех). Тело коммита и описание PR допустимо писать по-русски. Правило одно: внутри репозитория не смешивать языки заголовков. Окончательное решение — за автором (открытый вопрос 1).

**ИИ.** В проекте формируется AI Usage Policy (прозрачность: что, где и как сделано ИИ; технические тексты допустимо оставлять без правки, если они явно помечены; образовательное содержание обязательно проходит проверку человеком). Для git предлагается минимальное согласованное правило, которое нужно сверить с итоговой версией политики:

| Ситуация | Что делать |
| --- | --- |
| Коммит содержит существенную часть, написанную ИИ | В сноске указать соавтора: `Co-authored-by: Claude <noreply@anthropic.com>` |
| PR с текстом, созданным ИИ | В описании PR отметить строкой «LLM-generated: полностью / частично» и что именно |
| Образовательное содержание (текст книги, задания, код, иллюстрации) | В PR указать, кто проверил: автор, рецензент или эксперт. Проверка выполняется до слияния в `dev` |
| Внутренние инструкции для ИИ (скиллы, контекст) | Утверждаются человеком; в PR указывается, кто утвердил |

## 6. Связь с задачами (issues)

| Что | Как |
| --- | --- |
| Задача начинается | Issue → ветка от `dev` → draft PR |
| Коммит относится к задаче | Сноска `Refs #N` |
| PR завершает задачу | В описании PR: `Closes #N` |
| Несколько задач в одном PR | Допустимо только для мелких (опечатки): `Closes #N, closes #M` |
| Задача из другого репозитория | `Refs wolm-sdarp/book1#N` |
| Milestone | Назначается на issue, а при необходимости и на PR |

> **Оговорка.** GitHub автоматически закрывает issue по ключевому слову `Closes` только тогда, когда PR сливается в **основную (default) ветку** репозитория ([документация GitHub](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)). Основная ветка у нас `master`, а рабочие PR идут в `dev`, поэтому задачи **не закроются автоматически при слиянии в `dev`**: связь с PR сохранится, но issue останется открытым.

Варианты решения:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **A. Закрывать вручную** (рекомендуется на старте): после слияния нажать «Close as completed» и выбрать причину закрытия | Просто, ничего не настраивать, согласуется с правилами закрытия в gh-issues-docs | Легко забыть |
| B. Настроить в GitHub Projects встроенную автоматизацию (например, статус «Done» при слиянии PR или закрытии issue) | Доска всегда актуальна | Закрытие issue всё равно остаётся ручным |
| C. Сделать `dev` основной веткой репозитория | Автозакрытие работает | Читатель, открывший репозиторий, увидит `dev` с недоделанным, а не опубликованную версию. Для публичных репозиториев книг это плохо |
| D. Небольшой workflow, закрывающий issue по слиянию в `dev` | Автоматизация без смены основной ветки | Нужно писать и поддерживать |

Предлагается A, при росте объёма задач — D (открытый вопрос 3). C не рекомендуется.

## 7. Pull requests и слияние

### 7.1. Заголовок и описание

- **Заголовок PR оформляется как коммит** — `тип(область): описание`. При squash-слиянии он становится единственным коммитом в `dev`, поэтому заголовок проверяется особенно тщательно.
- **Описание** (шаблон ниже, в будущем — файл `.github/pull_request_template.md` для всей организации):

```markdown
## Что сделано
<!-- коротко: что изменилось и зачем -->

## Связанные задачи
Closes #

## Как проверить
<!-- что открыть или запустить; для текста — что именно перечитать -->

## Чек-лист
- [ ] Сборка проходит локально (`quarto render`) / код выполняется
- [ ] Метки и milestone выставлены
- [ ] Образовательное содержание проверено человеком (кем: …)
- [ ] Есть пометка о вкладе ИИ, если он был (LLM-generated: нет / частично / полностью)
```

- **Метки** — те же оси, что на issue (`ld:`, `content:`, `tech:`, `lang:`). Issue Types на PR не распространяются, поэтому тип виден по заголовку.
- **Размер:** один PR — одна задача; обычно хватает нескольких дней работы. Слишком большой PR невозможно рецензировать.
- **Draft PR** открывается сразу, как только есть первый коммит: так видно, что работа идёт, и можно получить ранний отзыв. «Ready for review» — когда работа завершена.
- **Самопроверка:** до запроса рецензии автор просматривает вкладку «Files changed» сам; половина лишних файлов и отладочных строк находится именно на этом шаге.
- Даже если участник один, **PR обязателен**: он оставляет описание, привязывает задачу и в будущем запускает автоматические проверки.

### 7.2. Способы слияния

| Откуда → куда | Способ | Заголовок слияния | Почему |
| --- | --- | --- | --- |
| рабочая ветка → `dev` | **Squash and merge** | заголовок PR | В `dev` одна запись на задачу; черновые коммиты не засоряют историю |
| `dev` → `master` (выпуск) | **Create a merge commit** | `chore(release): v1.2.0` или `chore(release): merge dev` | История `dev` сохраняется, ветки не расходятся |
| `hotfix/…` → `master` | Squash | заголовок PR | Резерв |
| рабочая ветка → `dev` при осмысленных коммитах (крупная перестройка) | Rebase and merge — исключение | — | Только если каждый коммит самостоятельно осмыслен; по умолчанию отключено |

**Почему `dev` → `master` нельзя делать через squash.** При squash создаётся новый коммит, и `dev` с `master` перестают иметь общую историю: при следующем выпуске PR показывает «старые» изменения как новые, возникают ложные конфликты. Поэтому squash — только для коротких веток, а долгоживущие `dev` и `master` соединяются обычным merge-коммитом.

После выпуска `dev` приводится в соответствие с `master`:

```bash
git switch dev && git pull
git merge --ff-only origin/master   # dev перемотается на merge-коммит
git push
```

### 7.3. После слияния

1. Ветка удаляется (включить в настройках «Automatically delete head branches»).
2. Локально: `git switch dev && git pull && git branch -d тип/описание`.
3. Issue закрывается (раздел 6) и передвигается на доске.

## 8. Релизы и теги (резерв)

Этот раздел описывает намерения. Он вступает в силу, когда будут выполнены условия из gh-issues-docs §9: принят SemVer и автоматизация релизов, выпущена первая stable-версия.

| Элемент | Предложение |
| --- | --- |
| Версия | `vMAJOR.MINOR.PATCH` для каждого репозитория отдельно (одна книга — один репозиторий, префикс проекта в теге не нужен) |
| MAJOR | Перестройка структуры или перенумерация, ломающие внешние ссылки (см. 5.6) |
| MINOR | Новая содержательная единица: глава, раздел, блок заданий |
| PATCH | Исправления и правки без изменения структуры |
| Предварительные версии | `v0.3.0-alpha.1`, `v0.3.0-beta.2` (каналы `channel:*`) |
| Тег | Аннотированный (`git tag -a v1.0.0 -m "…"`), ставится на `master` после слияния релизного PR |
| GitHub Release | Создаётся на основе тега; заметки автоматически формируются по меткам PR (файл `.github/release.yml`) |
| CHANGELOG | Для читателя ведётся вручную и по смыслу («что нового и что исправлено в тексте»), а не как список коммитов. Глобальный журнал проекта — `documentation/tech/CHANGELOG.md` |

Из-за единого формата коммитов позже можно подключить автоматическое определение версии и сбор заметок по типам (`feat` → minor, `fix` → patch, `!` → major), но для учебника итоговые заметки всё равно стоит редактировать вручную.

## 9. Что хранить в репозитории

### 9.1. Исходное — да, производное — нет

| Хранится | Не хранится |
| --- | --- |
| Исходные тексты (`.qmd`, `.md`), код (`.R`, `.py`), конфигурации (`_quarto.yml`) | Собранные книги и сайты: `_book/`, `_site/`, `docs/` с HTML (кроме случая публикации из папки) |
| `renv.lock`, `renv/activate.R`, `.Rprofile` | Библиотека пакетов `renv/library/` |
| Иллюстрации в исходном виде (предпочтительно SVG; растровые — разумного размера) | Рендеры видео, архивы, исходники большого размера |
| Небольшие учебные наборы данных (CSV до нескольких МБ) | Данные с персональной информацией, большие наборы |
| Кэш вычислений Quarto `_freeze/` — **по умолчанию да** (решение уточнить при настройке первой сборки) | Служебные каталоги `.quarto/`, `*_files/` |

### 9.2. Заготовка `.gitignore` для Quarto/R-репозитория

```gitignore
# RStudio / R
.Rproj.user/
.Rhistory
.RData
.Ruserdata
.Renviron          # секреты и токены

# Quarto
/.quarto/
/_book/
/_site/
*_files/
# _freeze/ НЕ игнорируется: кэш вычислений коммитится (уточнить)

# macOS / редакторы
.DS_Store
.obsidian/workspace*.json
```

Уточнение: `renv` сам создаёт `renv/.gitignore` и исключает свою библиотеку; `renv.lock` коммитится обязательно.

### 9.3. Заготовка `.gitattributes`

```gitattributes
* text=auto eol=lf
*.qmd text
*.R   text
renv.lock text
_freeze/** linguist-generated
```

Единые окончания строк избавляют от «призрачных» диффов при работе на разных системах.

### 9.4. Большие файлы

- GitHub предупреждает о файлах больше 50 МБ и не принимает больше 100 МБ; удалить уже попавший файл из истории сложно. Проверять размеры нужно до коммита.
- Видео `manim` не хранятся в репозитории: исходный код сцен — да, результат — как вложение к релизу (release assets) или на внешнем хостинге. Git LFS для проекта не рекомендуется (ограничения по квотам, сложность для читателей, которые клонируют репозиторий).

### 9.5. Секреты и персональные данные

Организация и репозитории открытые, поэтому всё, что попало в историю, считается опубликованным навсегда.

- Токены, ключи, пароли, `.Renviron` — только вне репозитория.
- Данные респондентов и студентов, неанонимизированные результаты опросов — не коммитятся.
- Если секрет всё же попал в историю, сначала его **отзывают** (меняют ключ), и только потом при необходимости чистят историю.
- Личная почта: в настройках GitHub включить «Keep my email addresses private» и использовать в `git config` адрес вида `ID+имя@users.noreply.github.com`. Иначе настоящий адрес окажется в каждом коммите.

## 11. Ежедневный цикл и «первая помощь»

### 11.1. Цикл одной задачи

```bash
# 1. Начать: свежий dev и новая ветка
git switch dev
git pull
git switch -c feat/pretests

# 2. Работать и коммитить по мере готовности логических шагов
git status
git add path/to/file.qmd            # или git add -p
git diff --staged                   # проверить, что именно попадёт в коммит
git commit -m "feat(ch05): add pretest for the p-value section"

# 3. Отправить и открыть PR (в dev)
git push
gh pr create --base dev --draft --title "feat(ch05): add pretests" --body "Refs #12"

# 4. Держать ветку свежей, пока идёт работа
git fetch origin
git rebase origin/dev               # только пока ветку никто, кроме тебя, не использует

# 5. Когда готово: PR → Ready for review → Squash and merge → удалить ветку
git switch dev && git pull
git branch -d feat/pretests
```

Те же шаги можно выполнять в GitHub Desktop или RStudio; важны порядок и имена, а не инструмент.

### 11.2. Что делать, если…

| Ситуация | Решение |
| --- | --- |
| Неправильное сообщение в последнем коммите (ещё не отправлен) | `git commit --amend` |
| Забыл файл в последнем коммите (не отправлен) | `git add файл && git commit --amend --no-edit` |
| Добавил лишний файл в индекс, но не закоммитил | `git restore --staged файл` |
| Хочу отменить несохранённые правки в файле | `git restore файл` (**необратимо**) |
| Нужно отложить работу и переключиться | `git stash`, потом `git stash pop` |
| Коммит уже отправлен, нужно «отменить» | `git revert <хеш>` — создаёт новый коммит-отмену; историю не переписывает |
| Коммит сделан не в той ветке (не отправлен) | `git switch нужная-ветка && git cherry-pick <хеш>`, затем в старой ветке `git reset --hard HEAD~1` (осторожно) |
| Конфликт при `rebase` или `merge` | Открыть файлы, найти `<<<<<<<`, оставить нужное, `git add файл`, `git rebase --continue` (или `git merge --continue`). Если запутался: `git rebase --abort` |
| «Потерялся» коммит или ветка | `git reflog` показывает все недавние положения HEAD; вернуться можно по хешу: `git switch -c rescue <хеш>` |
| Попал секрет или огромный файл | Сначала отозвать секрет; не пытаться «исправить» `push --force`; обратиться к ментору или разбираться по отдельной инструкции |
| Не уверен, что делаешь | `git status`, `git log --oneline -10`; скопировать вывод и спросить: чаще всего всё решается одной командой |

Правило безопасности: **необратимые команды** — `git reset --hard`, `git restore` (для неиндексированных правок), `git clean -fd`, `git push --force`. Перед ними — `git status`, и убедиться, что нужное закоммичено или лежит в `stash`.

### 11.3. Минимальный словарь

| Термин | Что означает |
| --- | --- |
| commit | Снимок изменений с описанием |
| branch | Подвижная метка на цепочке коммитов; «параллельная линия работы» |
| merge | Слияние веток |
| squash | Схлопывание всех коммитов ветки в один при слиянии |
| rebase | Перенос ветки на новое основание; переписывает историю, поэтому только для личных веток |
| PR (pull request) | Предложение влить ветку в другую, с обсуждением и проверками |
| tag | Постоянная метка на конкретном коммите, обычно версия |
| origin | Имя удалённого репозитория на GitHub |

## 14. Расширение правил

| Что вводится | Условие |
| --- | --- |
| Новый тип коммита | Появилась повторяющаяся работа, не укладывающаяся в существующие типы, и для неё нет Issue Type. Заводить сначала Issue Type (gh-issues-docs §9), затем одноимённый тип коммита |
